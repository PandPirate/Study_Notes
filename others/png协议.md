# PNG 二进制协议解析

PNG 文件 = **固定的 8 字节签名** + 一串 **chunk（数据块）**。
所有多字节整数一律使用**大端序（big-endian）**。

## 1. 文件签名（8 字节）

```
89 50 4E 47 0D 0A 1A 0A
```

即 `\x89` + ASCII `"PNG"` + `\r\n\x1a\n`。
首字节高位为 1，用于区分文本/二进制；这 8 字节用于判断文件是否为 PNG。

## 2. 通用 chunk 结构

每个 chunk 固定为四段式，**CRC 只覆盖 Type + Data（不含 Length）**：

| 字段 | 长度 | 说明 |
|---|---|---|
| Length | 4 字节 | Data 区字节数（不含 Length、Type、CRC 本身） |
| Type | 4 字节 | 4 个 ASCII 字母，如 `IHDR` |
| Data | Length 字节 | 内容视 Type 而定，可为空（Length=0） |
| CRC | 4 字节 | 对 Type+Data 计算 CRC-32，大端序写入 |

Type 字母大小写有语义：**首字母大写 = 关键块**（不认识必须报错）；首字母小写 = 辅助块（不认识可安全跳过）。

## 3. 关键块（顺序固定）

| 顺序 | 块 | 作用 |
|---|---|---|
| 1 | `IHDR` | 图像头，**必须是第一个 chunk**，Data 固定 13 字节 |
| 2 | `PLTE` | 调色板（仅索引色必选，真彩/灰度可作可选提示） |
| 3 | `IDAT` | 图像像素数据（压缩流），可连续多个、必须相邻，解码时拼接 |
| 4 | `IEND` | 结束标记，Length=0、Data 为空，**必须是最后一个** |

## 4. IHDR 布局（13 字节）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | Width | 宽（像素），≠0 |
| 4 | 4 | Height | 高（像素），≠0 |
| 8 | 1 | Bit depth | 位深：1/2/4/8/16，按颜色类型限用 |
| 9 | 1 | Color type | 颜色类型（见下表） |
| 10 | 1 | Compression | 压缩方法，现仅允许 0 = zlib/Deflate |
| 11 | 1 | Filter method | 滤波方法，现仅允许 0 |
| 12 | 1 | Interlace | 0 = 逐行；1 = Adam7 隔行扫描 |

## 5. 颜色类型

| 值 | 含义 | 位深允许值 | 每像素样本 |
|---|---|---|---|
| 0 | 灰度 | 1/2/4/8/16 | 1 个灰度值 |
| 2 | 真彩 RGB | 8/16 | R、G、B |
| 3 | 索引色 | 1/2/4/8 | 1 个调色板下标（须配 PLTE） |
| 4 | 灰度 + Alpha | 8/16 | 灰度、透明度 |
| 6 | RGBA | 8/16 | R、G、B、A |

位深 16 时每个样本占 2 字节，仍为大端序。

## 6. IDAT 像素数据的解码链路

```
所有 IDAT 的 Data 拼接
  → Deflate 解压（zlib 流）
  → 得到"滤波后"的逐行字节流
  → 按行反向还原滤波
  → 得到原始像素样本
```

要点：

- 每行以 **1 个滤波类型字节（0–4）开头**，后跟该行的滤波数据。
- 行字节数 stride ≈ `ceil(宽 × 每像素位数 / 8)`；位深不足 1 字节时，行尾留填充位，同一字节内左边像素在高位。
- **bpp（滤波步长）** = 每像素完整字节数，最少为 1（如 8 位索引色 = 1，8 位 RGB = 3，16 位 RGBA = 8）。

## 7. 五种行滤波（存储差分，解码反向加回）

| 值 | 名称 | 做法 |
|---|---|---|
| 0 | None | 原样存储 |
| 1 | Sub | 与本行左侧隔 bpp 字节的字节差分 |
| 2 | Up | 与上一行同列字节差分 |
| 3 | Average | 与 (左 + 上)/2 的**下取整均值**差分 |
| 4 | Paeth | 令 p = 左 + 上 − 左上；取左/上/左上中与 p **差的绝对值最小**者作预测，再差分 |

所有运算按字节**模 256**。第一行上侧视为 0；行首的左侧、左上视为 0。
滤波以"字节"为单位进行，与位深无关，这正是 bpp 作为步长的原因。

## 8. 常见辅助块

| 块 | 作用 |
|---|---|
| `tRNS` | 透明信息：索引色为每项一个 alpha；灰度/真彩为单一透明色样本 |
| `pHYs` | 物理像素密度（PPI/DPI） |
| `gAMA` / `cHRM` / `iCCP` | 颜色管理 |
| `tEXt` / `zTXt` / `iTXt` | 文本 / 压缩文本 / 国际化文本元数据 |
| `tIME` | 最近修改时间 |
| `eXIf` | EXIF |

## 9. CRC-32 说明

- 算法：标准 IEEE CRC-32（zlib 同款）——初值 `0xFFFFFFFF`，多项式 `0xEDB88320`，结果再异或 `0xFFFFFFFF`。
- 覆盖范围：**Type 4 字节 + Data**（Length 与 CRC 自身不参与）。
- 结果以 4 字节**大端序**写入 chunk 末尾。
- 作用：**检错**——检测传输/存储中的意外损坏（比特翻转、截断、拷贝错误）。它**不是加密、也不能防篡改**：CRC 无抗碰撞设计，任何人都能重算后写回。
- 校验示例：`IHDR` + 宽高 0x800×0x800、位深 8、RGBA、无隔行 的 17 字节，CRC-32 = `B2 A7 D3 30`。

## 10. CRC 不对时的行为

CRC 只是冗余校验，是否报错取决于解码器的实现严格程度：

- **严格实现**（如 `pngcheck`）：校验关键块 CRC，不匹配即报 `CRC error`，整张图拒绝打开。
- **宽松实现**（多数看图器/库默认）：忽略或仅警告，照常解码出图。

分情况看后果：

| 错误位置 | 后果 |
|---|---|
| 只有 CRC 4 字节错，其余字段都对 | 宽松实现照常出图；严格实现报错拒开。CRC 是冗余，不代表数据本身坏了 |
| 数据字段本身坏（CRC 即使重算正确） | CRC 只保证字节没传错，不保证参数与数据配套，解码器会拿错误参数照单执行，结果取决于坏哪个字段（见下表） |

字段坏了的典型表现：

| 字段 | 后果 |
|---|---|
| 宽 | 行字节数（stride）错位 → 花屏或报长度不匹配 |
| 高 | 改小：可能只显示顶部若干行；改大：行数不足 → 脏数据或报错 |
| 位深 / 颜色类型 | 每像素字节数（bpp）、通道解释错 → 色彩错乱 |
| 隔行位 | 与 Adam7 结构不符 → 花屏 |
| 压缩 / 滤波方法字段 | 规范只允许 0，改为非 0 属非法参数 → 解码器直接报错 |

其他要点：

- `IDAT` 内部是 zlib 流，自带 **Adler-32** 第二道完整性校验；而 IHDR 等字段**没有内部校验**，CRC 是唯一防线。
- CRC 不防恶意篡改：对不可信 PNG，防“解压炸弹/畸形宽高”要靠解码器自身的尺寸/资源上限，而不是 CRC。
- 排错建议：手工拼 PNG 遇到“CRC 报错”，优先怀疑 Length 或数据字段本身，而不是 CRC；用 `pngcheck` 可逐块校验并定位到具体 chunk。

## 11. IHDR 参数与 IDAT 必须配套（改字段为何花屏）

IHDR 是 IDAT 的“解读说明书”，IDAT 里的数据是按旧参数编码的。只改 IHDR（即使 CRC 也改对），解码器就会用新参数去解读旧数据，从第一行起字节错位并逐行累积，表现为**花屏/彩色噪点**。

原因链条：

1. IDAT 的滤波按行进行，而每行 stride、滤波步长 bpp 都由 IHDR 的宽/位深/颜色类型推导；
2. 每行开头还有 1 字节滤波类型，决定如何还原该行；
3. 参数一变，行内/行间的边界全部错位，且错误逐行累积。

所以：**改 IHDR 必须同步重编 IDAT**，正确流程为：

1. 按原 IHDR 完整解码（拼接 IDAT → zlib 解压 → 逐行解滤波）得到原始像素；
2. 在像素层面做需要的操作（缩放、改通道、改位深）；
3. 按新参数重新滤波、重新 zlib 压缩，生成新 IDAT；
4. 更新 IHDR（含新 CRC），必要时同步更新 PLTE / tRNS。

例外：**只把高度改小**（相当于裁掉底部若干行）可能可行，因为行按顺序独立解码、滤波只参考上一行；但只影响高度，不影响宽度。

## 12. IHDR chunk 完整示例

一个 2048×2048、RGBA8、无隔行的 PNG 文件开头：

```
89 50 4E 47 0D 0A 1A 0A    签名
00 00 00 0D                Length = 13
49 48 44 52                "IHDR"
00 00 08 00                宽 = 0x800 = 2048
00 00 08 00                高 = 0x800 = 2048
08                         位深 = 8
06                         颜色类型 = 6（RGBA）
00 00 00                   压缩=0 滤波=0 隔行=0
B2 A7 D3 30                CRC-32(Type+Data)
```

## 13. Adam7 隔行扫描（简述）

`Interlace = 1` 时，像素数据按 **Adam7** 分成 7 遍写入，每遍使用不同的起始偏移与步长，覆盖 8×8 网格的一个子集：

- 第 1 遍即可得到 1/8 宽、1/8 高的缩略预览；
- 解码须先把 7 遍分别解滤波还原，再按各自的 (x偏移, y偏移, x步长, y步长) 规则填回全图网格。

## 14. 协议级解析流程

1. 读前 8 字节，校验签名；
2. 循环读 chunk：Length → Type → Data → CRC，并用 Type+Data 重算 CRC 校验；
3. 解析 `IHDR`，得到宽、高、位深、颜色类型、隔行模式；
4. 校验关键块顺序/数量与参数组合的合法性；
5. 拼接全部 `IDAT` → zlib 解压 → 逐行解滤波 → 按颜色类型解释样本；
6. `Interlace = 1` 时按 Adam7 规则重排；
7. 读到 `IEND` 结束。

## 15. 从文件读宽高 & 篡改后恢复原始宽高

### 15.1 IHDR 没被改：直接从字节读

文件偏移（从文件头 0 开始计）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0–7 | 8 | 签名 |
| 8–11 | 4 | Length = `00 00 00 0D` |
| 12–15 | 4 | Type = `"IHDR"` |
| **16–19** | 4 | **Width（大端序）** |
| **20–23** | 4 | **Height（大端序）** |
| 24–36 | 13 | 位深 / 颜色类型 / 压缩 / 滤波 / 隔行 |

例：`16–19` = `00 00 08 00` → 宽 = 0x800 = 2048；`20–23` 同理为高。
`file`、`identify`、`pngcheck` 等工具显示的同样只是 IHDR 里这两个值，不是“原始值”。

### 15.2 IHDR 宽高被篡改：找回原始值

**① CRC 字段未被覆盖重算（只改了宽高字节）**

CRC 覆盖 Type+Data，等于把宽高的“指纹”留在文件里。枚举候选宽高，逐个重算
`CRC32("IHDR" + 宽 + 高 + 其余 9 字节)`，与文件里存储的 CRC 相等的那组即**原始宽高**。
宽高写错时 CRC 必然不匹配，所以穷举可唯一命中（先按常见尺寸/长宽比枚举，而非全空间）。

**② CRC 也被重算（自洽了）**

CRC 途径失效，改从 IDAT 结构反推：

1. 拼接全部 IDAT 并 zlib 解压，得滤波后总字节数 N；
2. 无隔行时每行 = 1 字节滤波类型 + stride 字节，即 `N = 高 × (1 + stride)`，`stride = ceil(宽 × bpp / 8)`，bpp 由颜色类型/位深决定；
3. 对 N 因子分解：每个因子当作“高”，反推 stride 与“宽”，校验宽是否合法整数且能还原回原 stride——能成立的 (宽, 高) 通常很少，再用图片比例/常见尺寸排除；
4. 辅助佐证：解压流每行首字节为滤波类型 0–4，用候选 stride 切分并统计首字节是否都落在 0–4，命中率更高；
5. 若隔行位 = 1（Adam7），行数与高不再相等，需按 7 遍结构反推，复杂得多。

**③ 外部来源**

原文件名、网页原图、发送方截图属性等外部信息可直接给出答案。

原理说明：该反推方法利用的正是第 11 节讲的**行结构与 IHDR 参数强耦合**——字段一改 IDAT 结构就对不上，反过来也能从结构恢复参数。

## 16. 用 vim + xxd 修改字段（实操：高度 900 → 1024）

vim 不提供原生十六进制模式，通用做法是把文件在**二进制 hexdump** 与二进制之间互转。

### 16.1 步骤（全程 5 条命令，不移动光标、不按其他键）

```
vim -b 文件.png        # 必须 -b 二进制模式（Windows 文本模式会把 0x1A 当 EOF）
:%!xxd                # 当前文件 -> hexdump 文本
:2s/0000 0384/0000 0400/   # 只改第 2 行：高 900(0x384) -> 1024(0x400)
:%!xxd -r             # hexdump 文本 -> 二进制
:wq
```

要点：

- 文件第 1 行是签名（0x00 行），**第 2 行（0x10 行）**才含宽高；`0000 0800` 是宽 2048（别动），`0000 0384` 是高。
- 用 `:2s/.../.../` 限定行 + 等长替换，避免手改误删。
- 保存后**文件大小必须保持不变**（本例 1,806,353 字节）。

### 16.2 为什么容易坏 & 怎么避免

- hexdump 里 **1 字节 = 2 个 hex 字符，每行 = 16 字节**；删 1 个字符 = 少半个字节，删 1 行 = 少 16 字节，后面全部错位 → 花屏。
- 禁止按键：`dd`（删行）、`D`、`x`、`d` 组合、退格；只允许替换命令。
- 别碰右侧 ASCII 列；改错立刻 `:q!` 退出重来，**不要保存**。
- vim 里直接打开 PNG 看必然乱码，这是正常的；用**图片查看器**确认结果。

### 16.3 CRC 怎么办

- 本例存储的 CRC（`75 07 B9 44`）恰好是原始 1024 高度头的指纹，所以**不用改 CRC**；
- 改成其他尺寸时 CRC 必须重算，写入偏移 0x1D–0x20，否则严格解码器报 `CRC error` 拒开。

### 16.4 跨机 / Samba 共享场景

- 编辑端（Linux vim）与查看端（Windows）必须是**同一个文件**：两侧 `ls -l` 大小一致、`md5sum` 一致；
- 编辑前**关闭残留 vim 会话**（旧 buffer 保存会覆盖新文件，造成“每次修复后又被覆盖成同样损坏”）；vim 加 `-n` 可避免在共享目录留 `.swp`；
- Windows 看图器/缩略图有缓存：完全关闭重开，或**复制到本地桌面再打开**排除缓存。
